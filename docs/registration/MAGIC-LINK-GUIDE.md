# Magic Link Guide — Buyer Guest Registration

## How Magic Links Work

A magic link is a unique URL sent to the buyer (the person who made the booking) so they can fill in guest names without needing a SWA Portal login.

### Step-by-step flow

1. **Admin creates a booking** with a buyer email address
2. **Admin clicks "Send Magic Link"** on the booking detail page
3. **System generates a 128-bit random token** and stores it in the `reg_tokens` database table linked to that booking
4. **Buyer receives an email** from SWA Portal with a "Register My Guests" button linking to `/reg/buyer/?token=<token>`
5. **Buyer clicks the link** — the buyer form page loads, validates the token, and shows all guest slots for that booking
6. **Buyer fills in names one at a time** — each name saved individually via a per-row Save button
7. **After the cut-off time**, the form shows a "registration closed" message and no further changes are accepted

Alternative: Admin can click **"Copy Link"** instead of sending an email. This copies the URL to the clipboard for manual sharing via WhatsApp, SMS, or in person.

---

## URL Anatomy

The buyer form URL looks like this:

```
https://admin.singaporewomenassociation.org/reg/buyer/?token=a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6
```

| Component | Description |
|-----------|-------------|
| Base URL | `https://admin.singaporewomenassociation.org/reg/buyer/` |
| Token parameter | `?token=` followed by a 32-character hex string |

The token is a 128-bit random value generated by `crypto.getRandomValues()` in the Cloudflare Worker runtime. It is not derived from any personal information and is not predictable.

## Security Model

### Token generation

- 128-bit random token via `crypto.getRandomValues(new Uint8Array(16))`
- Not guessable, not derived from booking data, not sequential
- Stored in D1 `reg_tokens` table with columns: `token` (PK), `booking_id` (FK), `created_at`, `expires_at`

### Token validation

- Both `GET /api/reg/buyer/:token` and `PATCH /api/reg/buyer/:token/guests/:id` validate the token server-side
- Validation checks: (1) token exists in `reg_tokens`, (2) `expires_at` has not passed
- If either check fails, the API returns `{ closed: true, reason: 'invalid' }` or `{ closed: true, reason: 'cutoff' }`
- The buyer form page shows an appropriate error message for each case

### Authentication bypass

- Buyer routes (`/api/reg/buyer/*`) bypass session authentication entirely
- No SWA Portal login is required to access the buyer form
- This is intentional — buyers are external parties (companies, individuals) who should not need SWA credentials

### No search engine indexing

- The buyer form page includes `<meta name="robots" content="noindex, nofollow, noarchive">`
- Tokens are not listed in any sitemap or public page
- The only way to reach a buyer form is via the token URL

### Token reuse

- `getOrCreateToken()` checks if a valid (non-expired) token already exists for a booking before creating a new one
- If an admin clicks "Send Magic Link" multiple times, the same token is reused if it has not expired
- If the existing token has expired, a new one is created with the current `formCutoffTime`

### Data scope

- A token grants access to guest names for **one booking only**
- The `PATCH` endpoint validates that the guest being edited belongs to the booking linked to the token
- A token cannot be used to read or modify any other booking's data

## What Happens If the Link Is Forwarded

**Anyone with the link can access the form and edit guest names for that booking.**

The token is bearer-based — whoever holds it can use it. This is by design, because:

1. **Delegation is expected.** A company representative may forward the link to an assistant or colleague to fill in guest names on their behalf.
2. **No user account required.** Buyers are external parties. Forcing them to create accounts would reduce participation.
3. **The link is unique per booking**, not per person. There is no concept of "buyer identity verification" beyond possessing the token.
4. **Changes are incremental.** Each name is saved individually. There is no "delete all" or destructive action available on the buyer form.

### Risk mitigations

| Risk | Mitigation |
|------|------------|
| Unauthorised person edits names | Admin can see all changes in the booking detail page and manually revert any name |
| Link leaked publicly | Token is 128-bit random. Not guessable. If compromised, admin can delete the token row from D1 and generate a new one |
| Malicious edits after cutoff | Form closes at `formCutoffTime`. No further changes accepted after cutoff |
| Link shared to wrong person | Each save is individual. The worst case is names being changed, which admin can detect and revert |

### Re-sending and invalidation

- **Re-send**: Admin clicks "Send Magic Link" again. If the existing token has not expired, the same link is sent. If expired, a new token is generated.
- **Manual invalidation**: `npx wrangler d1 execute swa-portal --remote --command="DELETE FROM reg_tokens WHERE booking_id = '<booking-id>'"` — this immediately revokes access. Admin can then generate a new token.
- **Full revocation of all tokens**: `npx wrangler d1 execute swa-portal --remote --command="DELETE FROM reg_tokens;"` — revokes all buyer form access. New tokens must be generated individually.

## Expiry and Cut-off Time

The `formCutoffTime` is stored in KV under `swa:reg_tables_config`:

```json
{
  "formCutoffTime": "2026-06-20T18:00:00+08:00",
  "tables": [...]
}
```

### How expiry works

| Event | What happens |
|-------|-------------|
| Token created | `expires_at` is set to the current `formCutoffTime` from KV |
| Buyer opens link before cutoff | Form loads normally, guest names shown and editable |
| Buyer opens link after cutoff | API returns `{ closed: true, reason: 'cutoff' }`. Page shows "registration closed" message |
| Token does not exist in database | API returns `{ closed: true, reason: 'invalid' }`. Page shows "invalid or expired link" message |

### Important: changing the cut-off time

When you update `formCutoffTime` in KV, **existing tokens keep their original `expires_at` value**. The expiry is stored in the `reg_tokens` row at token creation time, not checked against KV at runtime.

| Scenario | Result |
|----------|--------|
| Extend cutoff from 18:00 to 20:00 | Existing tokens still expire at 18:00. New tokens (created after the KV change) expire at 20:00. To extend existing tokens, delete them and re-send magic links. |
| Shorten cutoff from 18:00 to 16:00 | Existing tokens expire at 18:00 (later than new cutoff). The form also checks `isFormOpen()` against KV, so the form closes at 16:00 regardless of token expiry. |

If you need to extend the deadline for buyers who already have tokens, you must:

1. Update `formCutoffTime` in KV
2. Delete all tokens: `npx wrangler d1 execute swa-portal --remote --command="DELETE FROM reg_tokens;"`
3. Re-send magic links from the admin interface

## Admin Controls

| Action | Where | What it does |
|--------|-------|-------------|
| Send Magic Link | Booking detail page | Creates or retrieves token, sends email via Resend |
| Copy Link | Booking detail page | Creates or retrieves token, copies URL to clipboard |
| Invalidate a token | Wrangler CLI | `DELETE FROM reg_tokens WHERE booking_id = '...'` |
| Invalidate all tokens | Wrangler CLI | `DELETE FROM reg_tokens;` |
| Change cut-off time | Wrangler CLI | Update `swa:reg_tables_config` in KV (does not retroactively change existing token expiry) |
| Re-send after cut-off change | Admin UI | Delete old tokens first, then click Send Magic Link again |

## Troubleshooting

### Buyer says the link is not working

1. Check if the token exists: `npx wrangler d1 execute swa-portal --remote --command="SELECT * FROM reg_tokens WHERE token = '<token-from-url>';"`
2. Check if `expires_at` has passed
3. Check if the booking still exists: `npx wrangler d1 execute swa-portal --remote --command="SELECT * FROM reg_bookings WHERE id = '<booking-id>';"`
4. If expired or missing, delete the old token and re-send from admin UI

### Buyer says they did not receive the email

1. Check spam/junk folder
2. Verify the buyer email is correct in the booking detail page
3. Use "Copy Link" instead and share via WhatsApp/SMS
4. Check Resend dashboard for delivery status

### Buyer wants to make changes after the cut-off

- The form is closed. No changes can be made via the buyer form after `formCutoffTime`.
- Admin can still edit guest names directly in the booking detail page. The cut-off only affects the buyer form.
- To temporarily reopen: extend `formCutoffTime` in KV, delete existing tokens, and re-send magic links.

### Token was compromised or leaked

1. `npx wrangler d1 execute swa-portal --remote --command="DELETE FROM reg_tokens WHERE booking_id = '<booking-id>';"`
2. Go to admin UI, booking detail, click "Send Magic Link" to generate a fresh token
3. Share the new link with the buyer via a secure channel
